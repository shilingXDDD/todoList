## 一、🔴 严重问题（功能失效 / 数据丢失）

### 1. 编辑保存会清空所有附加字段

**位置**：`TaskEditActivity.saveTask()`

**错误代码**：

```kotlin
TaskRepository.updateTask(
    Task(taskId, title, description, isCompleted)     // ❌
)
```

**原因**：`Task` 有 **11 个字段**，这里只用位置参数传了前 4 个。
Kotlin 会用默认值补齐剩下 7 个——等于每次编辑保存都把
`category`、`priority`、`dueDate`、`reminderTime`、`note`、`link`、`createdAt` 全部重置。

**表现**：设置好分类 → 保存 → 再编辑改个标题 → 保存 → **分类没了**。

**修法**：用 `copy()` 保留原有字段

```kotlin
val existing = TaskRepository.getTaskById(taskId)
if (existing != null) {
    TaskRepository.updateTask(
        existing.copy(title = title, description = description, isCompleted = isCompleted)
    )
}
```

**状态**：✅ 已修

---

### 2. 分类选了但存不进去

**位置**：`TaskEditActivity.saveTask()`

**原因**：修完问题 1 用了 `copy()`，但**忘了把 `category` 放进 copy 参数**。

```kotlin
existing.copy(
    title = title,
    description = description,
    isCompleted = isCompleted
    // ← 没有 category，所以永远是默认的"默认"
)
```

**表现**：分类能选、能回显（回显读的是 `task.category`），
但**改完保存后分类永远是"默认"**。

⚠️ 这个坑很隐蔽：回显正常会让人误以为功能是好的，
只有"改完再存"才会暴露。而评分表明确写了
「无法保存的不视为完整的需求附加」——**这 2 分直接拿不到**。

**修法**：

```kotlin
// ⚠️ 在协程外先取 Spinner 值，不要等到协程里再取
val category = binding.categorySpinner.selectedItem?.toString() ?: "默认"

existing.copy(
    title = title,
    description = description,
    isCompleted = isCompleted,
    category = category          // ← 补上
)
```

**状态**：✅ 已修（编辑 + 新增两处都补了）

### 3. 搜索框完全不生效

**位置**：`TaskListFragment`

**原因**：`setupSearch()` 方法**定义了但从未调用**。
`onViewCreated` 里有 `setupRecyclerView()`、`observeTasks()`，
唯独漏了 `setupSearch()`。

**表现**：搜索框能看见、能输入，但列表毫无反应——**且不报任何错**。

**修法**：

```kotlin
override fun onViewCreated(view: View, savedInstanceState: Bundle?) {
    super.onViewCreated(view, savedInstanceState)
    setupRecyclerView()
    setupSearch()          // ← 补上
    observeTasks()
    ...
}
```

**状态**：✅ 已修

### 4. `strings.xml` 用了 `//` 注释导致整个项目编译失败

**错误代码**：

```xml
//%转义                                          <!-- ❌ XML 不认 // -->
<string name="stats_rate_value">%1$d%%</string>
```

**原因**：`//` 是 Java / Kotlin 的注释语法，**XML 必须用 `<!-- -->`**。

**表现**：aapt 报 `error: not well-formed (invalid token)`，
整个项目编译不过——而且报错位置可能不指向这一行，很难定位。

**修法**：

```xml
<!-- % 在 strings.xml 里必须转义成 %% -->
<string name="stats_rate_value">%1$d%%</string>
```

**状态**：✅ 已修

### 5. 统计页完成率显示 `NaN`

**位置**：`StatisticsActivity`

**错误代码**：

```kotlin
val rate = completed / total * 100      // ❌ 两个错
```

**两个问题**：

1. **除数为 0**：空列表时 `total = 0`，`0/0` 得到 `NaN`
2. **整数除法**：`completed / total` 先做整数除法得 `0`，再 ×100 还是 `0`

**表现**：空列表显示 `NaN%`；有数据时完成率一直显示 `0%`。

**修法**：先乘后除，并判断除零

```kotlin
val rate = if (total == 0) 0 else completed * 100 / total
```

**状态**：✅ 已修

### 6. 统计页两路 Flow 顺序导致闪现负数

**错误代码**：

```kotlin
launch {
    TaskRepository.countCompleted().collect { completed ->
        _completed = completed
        updateRate(_total, completed)     // ❌ _total 可能还是 0
    }
}
```

**原因**：`countCompleted` 先返回时 `_total` 还是初始值 0，
算出 `(0 - 2) = -2`，界面闪一下「未完成 -2」。

**修法**：先给字段赋值，再统一计算

```kotlin
private var total = 0
private var completed = 0

launch {
    TaskRepository.countAll().collect {
        total = it
        binding.txvTotal.text = it.toString()
        refreshDerived()          // 统一在这里算
    }
}

private fun refreshDerived() {
    binding.txvPending.text = (total - completed).toString()
    val rate = if (total == 0) 0 else completed * 100 / total
    binding.txvRate.text = getString(R.string.stats_rate_value, rate)
}
```

**状态**：✅ 已修

### 7. `onStop()` 注销广播可能崩溃

**位置**：`TaskListFragment.onStop()`

**错误代码**：

```kotlin
requireContext().unregisterReceiver(syncReceiver)     // ❌
```

**原因**：横竖屏切换时 Fragment 可能已与 Activity 解绑，
`requireContext()` 会抛 `IllegalStateException`。

**修法**：

```kotlin
val ctx = context ?: return
try {
    ctx.unregisterReceiver(syncReceiver)
} catch (e: IllegalArgumentException) {
    // 本来就没注册成功，忽略
}
```

**状态**：✅ 已修

### 8. Adapter 里直接用 `getString()` —— 编译错误

**位置**：`TaskAdapter.onBindViewHolder`（第四步 7.4 节）

**错误代码**：

```kotlin
holder.binding.dueDateTextView.text =
    getString(R.string.label_due_date, TimeUtil.format(task.dueDate))   // ❌
```

**原因**：`getString()` 是 `Context` 的方法，
`RecyclerView.Adapter` **不是** `Context`，直接调用编译不过。


⚠️ 同类问题：`holder.itemView.context` 在 Adapter 里等价于 Activity 的 `this`。

### 25. 🔥 PendingIntent 未携带 extra —— 定时提醒完全失效

**位置**：`util/ReminderManager.kt` → `pendingIntent()`

**错误代码**：

```kotlin
val intent = Intent(context, TaskReceiver::class.java).apply {
    action = TaskReceiver.ACTION_TASK_REMIND
}                                    // ← 没有 putExtra
```

**后果**：`TaskReceiver` 的 `getLongExtra(EXTRA_TASK_ID, -1L)` 拿到 `-1`，
走 `if (taskId == -1L) return`，**通知永远不弹**。

**关键认知**：extra 有两个作用，我只考虑了一个：

| 作用 | 是否参与 | 能否省略 |
|---|---|---|
| **匹配**（cancel 找到对应 alarm） | ❌ 不参与 | ✅ 可省 |
| **传递**（触发时 Receiver 取数据） | ✅ 原样传递 | ❌ **不可省** |

**修法**：`putExtra(EXTRA_TASK_ID, taskId)` + `putExtra(EXTRA_TASK_TITLE, title)`

**为什么难查**：不崩溃、不报错，只是安静地不工作。

**状态**：✅ 已修

### 26. 用了 `set()` 导致 Doze 下无限延迟

**原因**：Android 4.4 起 `set()` 不再精确，息屏后可能延迟几十分钟。

**修法**：优先 `setExactAndAllowWhileIdle`，无权限时退化 `setAndAllowWhileIdle`（都能在 Doze 下唤醒）。

**状态**：✅ 已修

### 27. Manifest 缺精确闹钟权限声明

**原因**：没声明 `SCHEDULE_EXACT_ALARM`，`canScheduleExactAlarms()` 恒 `false`，
导致第 26 条的分级判断永远走非精确分支。

**修法**：

```xml
<uses-permission android:name="android.permission.SCHEDULE_EXACT_ALARM"
                 android:maxSdkVersion="32" />
<uses-permission android:name="android.permission.USE_EXACT_ALARM" />
```

⚠️ Android 14 起该权限默认关闭，需用户手动开启。

**状态**：✅ 已修

### 28. 提醒时间秒被清零，比预期早响

**错误代码**：`set(year, month, day, hour, minute, 0)` —— 秒写死 0

**后果**：当前 14:30:45 选 14:31，实际 14:31:00 就响，只有 15 秒，和"1 分钟后"预期不符。

**修法**：`set(..., calendar.get(Calendar.SECOND))`，毫秒仍清零。

## 五、经验总结

### 5.1 三条血的教训

1. **`copy()` 优于重建对象**
   编辑更新一律 `existing.copy(...)`，永远不要 `Task(id, ...)`。
   加了新字段后，前者自动兼容，后者静默丢数据。

2. **定义了函数要记得调用**
   `setupSearch()` 定义了不调用，不报错、不崩溃，
   功能就是"安静地"不工作。这类 bug 最难发现。

3. **XML 注释用 `<!-- -->`**
   写惯 Kotlin 后容易顺手打 `//`，结果整个项目编译不过，
   且报错位置不直观。

### 5.2 文档写法改进

给代码示例前，必须确认引用的每个**资源 / 变量 / 方法当前确实存在**：

- 凡是要等后续章节才建的 → 拆成「最小版 + 增量版」
- 引用已删除的模板色（`purple_200` 等）→ 全部核对一遍
- 缺 import 的代码片段 → 一律补全再放进文档

### 5.3 自检口诀

```
改了布局 → 检查引用它的 Kotlin 还能不能编译
加了字段 → 检查 copy() 里有没有带上
写了函数 → 检查有没有被调用
用了 Spinner → 检查 adapter 是否在 setSelection 之前
建了 Intent → 检查 extra 有没有 putExtra          ← 第 25 条的教训
加了权限判断 → 检查 Manifest 有没有声明该权限      ← 第 27 条的教训
```

### 5.4 关于「不报错」的 bug

本次最难查的都不是崩溃，而是**安静地不工作**：

| 问题 | 现象 |
|---|---|
| `setupSearch()` 没调用 | 搜索框能输入，列表毫无反应 |
| `copy()` 漏传 category | 分类能回显，改完保存就没了 |
| PendingIntent 没放 extra | 闹钟到点，通知永远不弹 |

**共同点**：不崩溃、不报错、日志也没有异常。

**对策**：

1. **给关键路径加日志**——注册、触发、判空、执行每个环节都打点
2. **给关键操作加可见反馈**——Toast 明确告知成功/失败，别让人干等
3. **分层验证**——先验证最小环节（如"测试提醒"按钮），再验证完整链路
4. **优先怀疑数据没传到位**——extra / 参数 / 字段遗漏，而不是逻辑写错

### 5.5 一个反面教材：注释也可能误导人

第 25 条我写了这样的注释：

> "extra 不参与 PendingIntent 的匹配，所以取消时可以不带 extra。"

这句话单独看是**正确的**，但它让我误以为 extra 不重要，
于是在 `pendingIntent()` 里索性一个 extra 都没放。

**教训**：写注释时要说清楚**适用范围**。
"cancel 时不带 extra"是对的，但不能推广成"注册时也不用放"。

## 六、🔥 AlarmManager 定时提醒专章

> 这一章单独拿出来讲，因为它是本次**排查最久、也最典型**的一个问题：
> 现象是"等了 3 分钟通知没来"，但背后叠了**四个独立的原因**。
> 单独修任何一个都不够，必须四个都修才能跑通。

### 6.1 现象

```
新建任务 → 设置截止日期为「1 分钟后」→ 保存
→ 等 3 分钟 → 通知栏什么都没有
```

App 不崩溃、Logcat 也不报错，就是安静地不工作。

### 6.2 四个原因（按严重程度排序）

#### ❌ 原因一：PendingIntent 没放 extra —— **致命，通知永远弹不出来**

**位置**：`util/ReminderManager.kt` → `pendingIntent()`

**错误代码**：

```kotlin
private fun pendingIntent(context: Context, taskId: Long): PendingIntent {
    val intent = Intent(context, TaskReceiver::class.java).apply {
        action = TaskReceiver.ACTION_TASK_REMIND
    }                                    // ← 没有 putExtra！
    return PendingIntent.getBroadcast(context, taskId.toInt(), intent, ...)
}
```

**为什么错**：`TaskReceiver` 依赖 extra 取数据：

```kotlin
val taskId = intent.getLongExtra(EXTRA_TASK_ID, -1L)
if (taskId == -1L) {
    Log.w(TAG, "❌ taskId 无效，直接 return")
    return                               // ← 拿到 -1，直接返回
}
```

Intent 没放 extra → `getLongExtra` 返回默认值 `-1` → **直接 return，不弹通知**。

**我当时的错误认知**（写在了代码注释里）：

> "extra 不参与 PendingIntent 的匹配，所以取消时可以不带 extra。"

这句话**只对了一半**：

| 场景 | extra 的作用 | 能不能省略 |
|---|---|---|
| **匹配**（cancel 时找到对应 alarm） | 不参与匹配 | ✅ 可以省 |
| **传递**（触发时 Receiver 取数据） | 会原样传给 Receiver | ❌ **不能省** |

我只考虑了"匹配"，忽略了"传递"，导致注册的 alarm 虽然能触发、也能被取消，
但 Receiver 拿到的永远是空数据。

**修复**：

```kotlin
private fun pendingIntent(context: Context, taskId: Long, title: String = ""): PendingIntent {
    val intent = Intent(context, TaskReceiver::class.java).apply {
        action = TaskReceiver.ACTION_TASK_REMIND
        putExtra(TaskReceiver.EXTRA_TASK_ID, taskId)
        putExtra(TaskReceiver.EXTRA_TASK_TITLE, title)
    }
    return PendingIntent.getBroadcast(
        context, taskId.toInt(), intent,
        PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE
    )
}
```

调用处：

```kotlin
// schedule：必须传 title，否则通知标题是空的
val pi = pendingIntent(context, task.id, task.title)

// cancel：不用传 title（extra 不参与匹配，照样能取消）
val pi = pendingIntent(context, taskId)
```

---

#### ❌ 原因二：用了 `set()`，Doze 模式下会被无限延迟

**错误代码**：

```kotlin
alarmManager.set(AlarmManager.RTC_WAKEUP, remindAt, pi)     // ❌
```

**原因**：Android 4.4（API 19）起 `set()` 不再精确。系统为了省电会把多个 alarm
合并批处理，**息屏进入 Doze 后可能延迟几十分钟**。

**修复**：按权限情况分级

```kotlin
if (canScheduleExactAlarms(context)) {
    alarmManager.setExactAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, remindAt, pi)
    Log.d(TAG, "已注册精确提醒：taskId=${task.id} at ${TimeUtil.format(remindAt)}")
} else {
    alarmManager.setAndAllowWhileIdle(AlarmManager.RTC_WAKEUP, remindAt, pi)
    Log.w(TAG, "无精确闹钟权限，退化为非精确")
}
```

> `setAndAllowWhileIdle` 不需要额外权限，且能在 Doze 下唤醒，比 `set()` 可靠得多。

---

#### ❌ 原因三：Manifest 没声明精确闹钟权限

**原因**：没声明 `SCHEDULE_EXACT_ALARM`，`canScheduleExactAlarms()` 恒为 `false`，
导致原因二里**永远走非精确分支**，加了分级判断也没用。

**修复**：

```xml
<!-- Android 12（API 31）起需要声明；Android 14（API 34）起默认关闭 -->
<uses-permission
        android:name="android.permission.SCHEDULE_EXACT_ALARM"
        android:maxSdkVersion="32" />
<uses-permission android:name="android.permission.USE_EXACT_ALARM" />
```

⚠️ `SCHEDULE_EXACT_ALARM` 在 Android 14 起默认**拒绝**，
需要用户到 `设置 → 应用 → TodoList → 闹钟和提醒` 手动开启。

---

#### ❌ 原因四：秒被清零，实际提醒时间比预期早

**位置**：`TaskEditActivity.showDateTimePicker()`

**错误代码**：

```kotlin
set(year, month, day, hour, minute, 0)     // ← 秒写死 0
set(Calendar.MILLISECOND, 0)
```

**后果**：假设当前 14:30:45，你选 14:31 —— 实际提醒时间是 **14:31:00**，
只有 **15 秒**后就该响。和"1 分钟后"的预期完全不符，测试时会误判。

**修复**：秒沿用当前秒数

```kotlin
set(year, month, day, hour, minute, calendar.get(Calendar.SECOND))
set(Calendar.MILLISECOND, 0)   // 毫秒仍要清零（排序 / "是不是今天"的判断依赖它）
```

---

### 6.3 配套改进：让"有没有设上"变成可见的

原实现最大的问题是**反馈缺失**——注册成功还是失败，用户完全不知道，
只能干等着看通知来不来。已加：

**① 保存后 Toast 明确告知**

```kotlin
val msg = when {
    dueDate == null -> getString(R.string.msg_save_success)
    scheduled -> getString(R.string.msg_reminder_scheduled) + "：" + TimeUtil.format(dueDate)
    else -> getString(R.string.msg_reminder_time_past)
}
```

| Toast | 含义 |
|---|---|
| 保存成功 | 没设日期 |
| **提醒已设置：2026-09-14 15:30** | ✅ 注册成功 |
| 保存成功（提醒时间已过，未设置提醒） | 选了过去的时间 |

**② 注册 / 触发全程日志**

Logcat 过滤 `ReminderManager|TaskReceiver`，能看到：

```
ReminderManager: 已注册精确提醒：taskId=3 at 2026-09-14 15:30
TaskReceiver:    ① onReceive 被调用，action=com.example.todo_list.TASK_REMIND
TaskReceiver:    ② taskId=3, title=测试定时提醒
TaskReceiver:    ③ 通知总开关 areNotificationsEnabled = true
TaskReceiver:    ④ 渠道 importance=3
TaskReceiver:    ⑤ 调用 notify()，id=3
```

### 6.4 顺带修掉的逻辑漏洞：勾选完成后仍会提醒

**位置**：`TaskListFragment` → `onCheckedChange`

**问题**：勾选完成只更新了 `isCompleted`，**没有取消 Alarm**。
任务都做完了，到点还弹提醒。

**修复**：

```kotlin
val ctx = context ?: return@launch
if (isChecked) {
    ReminderManager.cancel(ctx, updated.id)      // 做完了就别再响
} else {
    ReminderManager.schedule(ctx, updated)       // 取消勾选，重新计时
}
```

### 6.5 修完之后的完整链路

```
设日期（未来）→ 保存
  → reminderTime = dueDate
  → schedule() 注册 alarm（带 extra）✅
  → Toast「提醒已设置：xx:xx」

到点
  → 系统发广播，extra 完整传递 ✅
  → Receiver: taskId ≠ -1 ✅
  → notify() 弹通知（标题 = 任务标题）✅

点通知 → 进详情页 ✅

删除任务 → cancel() → 到点不响 ✅
勾选完成 → cancel() → 到点不响 ✅
改日期   → 先 cancel 旧 → 再注册新 ✅
清日期   → cancel + 不注册 ✅
```

### 6.6 排查这类问题的方法论

**① 分层验证，不要一上来就等 3 分钟**

```
先用「测试提醒」按钮（立即发广播）验证通知链路
  ├─ 能弹 → 通知本身没问题，问题在 Alarm 定时
  └─ 不弹 → 问题在通知权限 / 渠道，跟 AlarmManager 无关
```

这一步能在 10 秒内把问题范围砍掉一半。

**② 用 adb 直接看 alarm 有没有注册上**

不用干等：

```powershell
adb shell dumpsys alarm | findstr todo_list
```

- 设置提醒**后**能看到条目 → Alarm 注册成功，问题在触发或通知环节
- 看不到 → 根本没注册上（`set()` 被延迟 / 时间已过 / 权限问题）

**③ 完整日志链**

注册、触发、判空、notify 每个环节都打日志。
卡在第几步一目了然，而不是靠猜。

**④ 警惕"不报错"的 bug**

这次的 extra 缺失**不崩溃、不报错**，只是安静地不工作。
这类 bug 比崩溃更难查——崩溃至少告诉你哪一行错了。

**判断标准**：凡是"功能没生效但没有任何错误提示"的，
优先怀疑**数据没传到位**（extra / 参数 / 字段遗漏），而不是逻辑写错。
