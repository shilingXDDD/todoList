### 1.3 Task 实体（对应"Room 基础结构"1 分）

评分表给出的核心字段：

```kotlin
@Entity(tableName = "tasks")
data class Task(
    @PrimaryKey(autoGenerate = true)
    val id: Long = 0,
    val title: String,
    val description: String = "",
    val isCompleted: Boolean = false
)
```

**必做就这 4 个字段。** 附加项在此基础上继续加，全部给默认值，避免影响必做部分：

| 附加字段 | 对应附加项 | 分值 |
|---|---|---|
| `category: String` | 任务分类 | 2 |
| `priority: Int` | 任务优先级 | 2 |
| `dueDate: Long?` | 日期/时间设置 | 2 |
| `reminderTime: Long?` | AlarmManager 定时提醒 | 2 |
| `note: String`、`link: String` | 备注、学习资料链接 | 2 |

**建议一次就按带附加字段的版本写。** 字段加了之后 UI 和 Dao 都要跟着改，后补的返工成本远高于一开始就预留。

### 1.4 TaskDao（对应"Dao 包含基本 CRUD"1 分）

必须覆盖 `insert / query / update / delete` 四类。返回 `Flow` 才能自动刷新列表：

```kotlin
@Dao
interface TaskDao {
    @Query("SELECT * FROM tasks ORDER BY id DESC")
    fun getAllTasks(): Flow<List<Task>>

    @Query("SELECT * FROM tasks WHERE id = :id")
    suspend fun getTaskById(id: Long): Task?

    @Insert
    suspend fun insertTask(task: Task): Long

    @Update
    suspend fun updateTask(task: Task)

    @Delete
    suspend fun deleteTask(task: Task)
}
```

这 5 个方法就是骨架。附加项再加：关键字搜索、按分类查、按优先级排序、统计数量。

### 1.5 AppDatabase（对应"Database 配置正确"1 分）

- `@Database(entities = [Task::class], version = 1, exportSchema = false)`
- 做成单例（`companion object` + `@Volatile` + `getInstance`），不要每次 `build()` 新实例
- 日后加 `category` 等字段时**必须 version +1 并提供 Migration**，否则老数据会崩

### 1.6 Room 持久化验收（对应"数据保存、查询、重启恢复"3 分）

三项都要能演示：

| 演示动作 | 分数 |
|---|---|
| 新增任务后数据正确 | 1 |
| 数据保存、重启后恢复 | 1 |
| 重启后改动仍存在 | 1 |

这是全表**最容易拿、也最容易丢**的 3 分。务必亲自**杀进程再重开**验证，不要只在页面间来回切。

### 1.7 数据库线程与页面刷新（对应"数据库线程与页面刷新"3 分）

评分表原文："数据库操作未直接在主线程执行得 1 分"。

- Room 的 `suspend` 函数必须从 `viewModelScope` 或 `lifecycleScope` 调用
- **绝对不要**写 `runBlocking { dao.insert(...) }`
- 用 `Flow` 收集，增删改查后列表**自动刷新**（占 1 分）

验收：新增 / 编辑 / 删除 / 切换完成状态，四种操作后列表都立刻正确显示，且**不卡顿**。

### 1.8 新增任务与标题校验（5 分）

### 1.10 查看详情 / 编辑 / 删除（11 分）

| 考点 | 分值 | 关键动作 |

### 2.1 三个 Activity 的分工（对应"Activity 职责"3 分）

| Activity | 职责 | 分值 |
|---|---|---|

### 2.2 Intent 跳转与参数传递（4 分）

| 考点 | 分值 | 做法 |
|---|---|---|
| 列表→详情 | 1 | `Intent(this, TaskDetailActivity::class.java).putExtra("task_id", id)` |
| 详情→编辑 | 1 | 同样传 `task_id` |
| 正确传递任务 ID | 1 | 传 **ID 而不是整个对象** |
| 根据 ID 加载正确任务 | 1 | 接收方用 ID 去 Room 查 |

ID 用 `Long` 传递，取值用 `getLongExtra(KEY, -1L)`，默认 `-1` 表示"新增模式"。这是新增/编辑复用的关键。

### 2.3 两个 Fragment（4 分）

`TaskListFragment`（2 分）、`SettingsFragment`（2 分）。

- `onCreateView()` 加载布局
- `onViewCreated()` 绑定 View、设监听、收集数据
- **不要在 `onCreateView` 里碰数据**，那时 View 还没好

### 2.4 BottomNavigationView 导航（3 分）

| 考点 | 分值 |
|---|---|
| 可以正常切换两个 Fragment | 2 |
| 切换后页面显示和交互正常 | 1 |

推荐用 `FragmentContainerView` + `supportFragmentManager.commit` 的 `show/hide` 方式（**不是 `replace`**）：

- `replace` 会销毁重建 Fragment，切回来数据要重新加载，容易闪
- `show/hide` 保留状态，切换更顺滑
- 记得 `addToBackStack(null)` 视需求决定，否则返回键行为要自己处理

### 2.5 返回列表的数据刷新（3 分）

**这是最容易被扣分的 3 分。** 评分表原文："从新增、编辑、详情页返回后列表可显示最新数据得 3 分。存在明显返回异常或数据不更新时酌情扣分。"

三种做法对比：

| 方案 | 评价 |
|---|---|
| `onResume` 里重新查一次数据库 | 简单可靠，**必做保底方案** |
| 用 Flow 收集（推荐） | 数据一变自动刷新，最优雅 |
| 用 `ActivityResultLauncher` 回调 | 也行，但要记得注册 |

**关键坑**：用 `Flow` 时，如果 `collect` 写在 `onViewCreated` 里、`launchWhenStarted` 又处理不当，会出现"返回后重复收集导致数据翻倍"。建议统一用 `repeatOnLifecycle(Lifecycle.State.STARTED)` 收集。

**验证方式**：新增一条 → 返回 → 列表必须立刻出现；编辑标题 → 返回 → 列表必须显示新标题。

### 2.6 生命周期基本使用（3 分）

| 考点 | 分值 |
|---|---|
| 合理使用 `onCreateView()`、`onViewCreated()` 等方法 | 2 |
| 避免在 Fragment View 销毁后继续访问 View | 1 |

第二条的典型写法：

```kotlin
private var _binding: FragmentTaskListBinding? = null
private val binding get() = _binding!!

override fun onCreateView(...): View {
    _binding = FragmentTaskListBinding.inflate(inflater, container, false)
    return binding.root
}

override fun onDestroyView() {
    super.onDestroyView()
    _binding = null          // ← 这一行就是那 1 分
}
```

用 ViewBinding 并置空，是"避免 View 销毁后继续访问"的标准答案。

## 四、Service、BroadcastReceiver 与通知（20 分）

这一块**独立于 Room**，可以单独开发测试，建议在数据层通了之后就做。

### 4.1 TaskSyncService（5 分）

| 考点 | 分值 |
|---|---|
| 点击"同步"可启动 Service | 1 |
| Service 模拟约 2 秒同步 | 2 |
| 完成后调用 `stopSelf()` | 1 |
| 不直接操作页面 View | 1 |

```kotlin
class TaskSyncService : Service() {
    override fun onStartCommand(...): Int {
        Thread {
            Thread.sleep(2000)        // 模拟耗时同步
            sendBroadcast(Intent(ACTION_SYNC_FINISHED)
                .setPackage(packageName))   // Android 8+ 必须指定包名
            stopSelf()
        }.start()
        return START_NOT_STICKY
    }
}
```

**坑**：
- 不要在 Service 里直接访问 `RecyclerView`，用广播通知页面（这就是"不直接操作 View"这 1 分）
- 用 `Thread.sleep` 只是"模拟"，必须在子线程，否则 ANR
- 更规范的做法是 `WorkManager`，但评分表要求 Service，别炫技

### 4.2 同步完成广播（4 分）

| 考点 | 分值 |
|---|---|
| Service 正确发送广播 | 1 |
| 任务列表页能接收广播 | 1 |
| 收到广播后显示同步完成提示 | 1 |
| 处理重复同步 | 1 |

**注册方式二选一**：

- **动态注册**（`onStart` 注册 / `onStop` 注销）→ 推荐，页面在才收，天然避免泄漏
- 静态注册 → Android 8.0+ 对隐式广播有限制，且页面销毁后仍会收到，容易崩

**"处理重复同步"的坑**：连点两次同步按钮会起两个 Service、发两次广播、弹两次 Toast。解决办法是用一个 `isSyncing` 布尔量拦截，同步中再点直接 return。

```kotlin
context.registerReceiver(receiver, IntentFilter(ACTION_SYNC_FINISHED),
    Context.RECEIVER_NOT_EXPORTED)     // Android 13+ 必须指定导出标志
```

> Android 14（targetSdk 34）下，动态注册广播**必须**加 `RECEIVER_NOT_EXPORTED` 或 `RECEIVER_EXPORTED`，否则直接崩。你的 `targetSdk` 是 34，这条必踩。

### 4.3 TaskReceiver（4 分）

| 考点 | 分值 |
|---|---|
| 详情页可发送显式提醒广播 | 1 |
| Receiver 能正确接收广播 | 1 |
| 广播中包含任务 ID 或任务标题 | 1 |
| 点击通知后进入对应详情页 | 1 |

"点击通知进入详情页"用 `PendingIntent`：

```kotlin
val intent = Intent(context, TaskDetailActivity::class.java)
    .putExtra("task_id", taskId)
val pi = PendingIntent.getActivity(context, taskId.toInt(), intent,
    PendingIntent.FLAG_UPDATE_CURRENT or PendingIntent.FLAG_IMMUTABLE)
```

**坑**：Android 12+ 要求 `PendingIntent` 必须显式指定 `FLAG_IMMUTABLE` 或 `FLAG_MUTABLE`，漏了会崩。`requestCode` 用 `taskId` 可以保证不同任务的通知互不覆盖。

### 4.4 通知显示与跳转（5 分）

| 考点 | 分值 |
|---|---|
| 正确创建通知渠道 | 1 |
| 成功显示通知 | 1 |
| 处理 Android 13+ 通知权限 | 1 |
| 通知内容包含任务信息 | 1 |
| 点击通知进入对应详情页 | 1 |

**通知渠道**（Android 8.0+ 必须）：

```kotlin
val channel = NotificationChannel(CHANNEL_ID, "任务提醒", IMPORTANCE_HIGH)
manager.createNotificationChannel(channel)
```

`CHANNEL_ID` 和渠道名要做成常量，重复创建同名渠道是安全的，不要每次随机生成 ID。

**Android 13+ 权限（这条最容易丢分）**：`targetSdk 34` 下必须在 Manifest 声明并**运行时申请**：

```xml
<uses-permission android:name="android.permission.POST_NOTIFICATIONS" />
```

```kotlin
if (Build.VERSION.SDK_INT >= 33) {
    registerForActivityResult(RequestPermission()) { }.launch(
        Manifest.permission.POST_NOTIFICATIONS)
}
```

不加的话在 Android 13+ 设备上通知**完全不显示**，第 2、4 两条分直接没了。

### 4.5 Receiver 使用规范（3 分）

| 考点 | 分值 |
|---|---|
| `onReceive()` 中不执行耗时任务 | 2 |
| Receiver 注册和注销方式合理 | 1 |

- `onReceive()` 在主线程执行，**超过 10 秒 ANR**。只做发通知这种轻量动作
- 耗时活交给 Service / WorkManager
- 动态注册务必在 `onStop` 或 `onDestroy` 注销，避免 `IntentReceiverLeaked`

## 五、设置、工程量与提交材料（15 分）

### 5.1 SharedPreferences 保存昵称（3 分）

| 考点 | 分值 |
|---|---|
| 可以保存昵称 | 1 |
| 设置页能读取并显示昵称 | 1 |
| 重启 App 后昵称仍存在 | 1 |

```kotlin
val sp = getSharedPreferences("app_settings", MODE_PRIVATE)
sp.edit().putString("nickname", name).apply()
```

**坑**：`apply()` 是异步写、`commit()` 是同步写。保存后立刻读要用 `commit()`，或者先更新 UI 再读。建议统一 `apply()`，读取时直接取内存值。

### 5.2 项目结构（2 分）

### 5.3 代码规范（2 分）

"类名、方法名、变量名和资源名基本规范得 1 分；代码格式清晰、无大量重复或无效代码得 1 分。"

零成本拿分项：

## 六、需求附加（19 分）

评分表 9.1 强调：**"仅增加数据库字段、但页面无法录入、保存或展示的，不视为完整的需求附加。"**

也就是说：加字段不算分，**字段要能在页面上录入 → 存进库 → 显示出来**，三步全通才算。

| 附加项 | 分值 | 三步验收 |
|---|---|---|
| 搜索任务 | 2 | 关键词搜索标题，有结果；**无匹配时要有明确提示** |
| 任务分类 | 2 | 学习/工作/生活等分类，可在列表或详情展示 |
| 任务优先级 | 2 | 高/中/低，列表或详情可见 |
| 任务筛选或排序 | 2 | 按完成状态筛选 **或** 按标题/创建时间排序，至少实现一种 |
| 统计页面 | 3 | 独立页面展示总任务数、已完成数、未完成数或完成率，**数据必须准确** |
| 任务日期或时间设置 | 2 | `DatePickerDialog` + `TimePickerDialog`，设置后能保存并显示 |
| AlarmManager 定时提醒 | 2 | 设置后到点能触发广播并显示通知 |
| 删除任务时取消提醒 | 2 | **删任务必须同步取消 Alarm 和 PendingIntent** |
| 任务备注、学习资料链接等扩展 | 2 | 增加字段，完成录入、保存、展示 |

### 两个高性价比项

**统计页面（3 分）**：一个独立 Activity，用 Dao 的 `COUNT` 查询 + 三个 `TextView` 就能拿满，投入产出比最高。

**搜索（2 分）**：`SearchView` + Dao 加一个 `WHERE title LIKE '%' || :kw || '%'` 即可。注意评分表特意强调"无匹配结果时有明确提示"，别忘了空结果文案。

### 两个容易踩的坑

**删除时取消提醒（2 分）**：必须在删除逻辑里同步做：

```kotlin
val am = context.getSystemService(AlarmManager::class.java)
am.cancel(pendingIntentFor(taskId))
```

只删数据库不取消 Alarm，到点还会弹出通知，然后点通知进详情页发现任务不存在 → 崩。这在答辩演示时很容易被抓。

**"二选一，不重复累计"**：ContentProvider 那条明确写了"查询任务 2 分"和"完整 CRUD 4 分"**二选一，不重复累计**。想做 ContentProvider 就冲着完整的 4 分去，别做一半。

### 优先级建议（按性价比）

1. **ViewModel + Repository（2 分）** —— 顺带解决"返回刷新"和生命周期那两个必做考点，一举多得
2. **单元测试（2 分）** —— 只要求"至少一个可运行的测试"，写个 Dao 的 CRUD 测试即可
3. **横竖屏状态恢复（2 分）** —— 用 `savedInstanceState` + `ViewModel` 保住输入内容
4. **深色模式（2 分）** —— 用 `values-night` + Material3 主题基本自动适配
5. **ContentProvider 完整 CRUD（4 分）** —— 分值最高但工作量也最大，放在后面
6. **ContentObserver（1 分）** —— 依赖 ContentProvider，一起做
7. **架构图（1 分）+ 演示视频（1 分）** —— 最后补，属于文档工作

### 横竖屏的具体坑

`TaskEditActivity` 里用户填了一半的标题，转屏后必须还在：

- 输入框需要 `android:id`（有 ID 才有自动保存恢复）
- 或者用 `onSaveInstanceState` 手动存
- 或者用 `ViewModel` 持有（推荐，和前面的 ViewModel 附加项共用一套代码）

### 深色模式的具体坑

你现在主题是 `Theme.Material3.DayNight.NoActionBar`，本来支持跟随系统。但要注意：

- 硬编码 `#FFFFFF` 的地方在深色下会出问题（白底白字）
- 颜色统一走 `colors.xml` + `values-night/colors.xml`
- 文字用 `?attr/colorOnSurface` 这类主题属性，不要写死
